# TP-Link TL-WDR4300 — primary CSI transmitter

Dual-band 802.11n (N750), 2.4 GHz + 5 GHz. No 802.11ac, no 60 GHz — irrelevant
here, since CSI only needs steady beacons.

## Access

| | |
|---|---|
| LAN address | `192.168.1.1` |
| Web UI | `http://192.168.1.1` — **DD-WRT v3.0-r30880 std (11/16/16)** |
| Login | `admin` / *(in the password manager)* |
| 5 GHz interface | `ath1`, 2.4 GHz is `ath0` |
| DHCP | enabled, hands out `192.168.1.x` |
| WAN port | **empty, intentionally** |

To reach it, cable this PC into one of the numbered **LAN** ports (not WAN) and
bring up the DHCP profile:

```bash
nmcli connection up router-setup      # DHCP; gives 192.168.1.x
# ... configure via browser ...
nmcli connection up "Wired connection 1"   # back to the Pi link (10.0.0.250 + NAT)
```

`router-setup` is a separate NetworkManager profile created for exactly this, so
the Pi's static/NAT configuration is never overwritten — the two just take turns
on the single Ethernet port.

## Wireless configuration

| | 2.4 GHz | 5 GHz |
|---|---|---|
| SSID | `nexmon-lab` | `nexmon-lab-5g` |
| **BSSID** | `60:E3:27:FB:61:53` | `60:E3:27:FB:61:54` |
| Channel | **1** (fixed) | **161** (fixed) |
| Frequency | 2412 MHz | 5805 MHz |
| Channel width | 20 MHz | 20 MHz |
| Wireless Network Mode | Mixed | **A-Only** |
| TX Antenna Chains | 1+2+3 | **1** |
| Short GI | — | **Disabled** |
| Security | WPA2-PSK (AES) | WPA2-PSK (AES) |

### TX Antenna Chains must be 1 — this is not optional

DD-WRT's default `1+2+3` transmits across all three chains, so consecutive
frames leave the router by different antennas and present a **different
channel** to the Pi. Measured on broadcast traffic before the change:

```
per-SC std total  4.94 dB
per-packet level  1.55 dB     <- common-mode, AGC-like
shape-only        4.72 dB     <- the frequency response itself, switching
```

Clustering the per-frame responses gave cluster means differing by up to
**20 dB** across subcarriers, with a median dwell of 1-2 frames. One cluster
was clean on its own (1.42 dB std, 5-apart correlation +0.615) against +0.277
pooled. That is antenna switching, not the environment - and it destroys any
measurement that reads the *shape* of the channel response, which is what
material characterisation does.

`Wireless Network Mode: A-Only` matters for a second reason: it forces legacy
single-stream OFDM. The Pi is 1x1 and **cannot decode a 2-stream
transmission at all**, so with a 2x2 client on an HT link the AP's replies
yield no CSI whatsoever (measured: 0-1 frames in 10 s).

**In DD-WRT, `Save` stores a setting and `Apply Settings` activates it.** A
setting that reads correctly in the UI but does not change the measured
behaviour has almost certainly only been saved. The tell for HT still being
live is `BlockAck` frames in a capture - block acknowledgement does not exist
in legacy 802.11a.

Also relevant, currently at defaults: **DTIM Interval 2** buffers broadcast
for two beacon periods and shows up as gaps in a broadcast capture; set it to
1 if collecting with `--traffic bcast`.

The two BSSIDs differ by one in the last octet — the radios share a base MAC.
`60:E3:27` is a TP-Link OUI.

### Why these choices

**Channel must be fixed, never `Auto`.** On Auto the router rescans and hops
bands. The Pi's CSI chanspec then points at a channel nothing is transmitting on,
and captures come back empty **with no error** — `tcpdump` simply sits there. This
is the single most likely cause of "CSI stopped working" and the first thing to
check.

**Channel 161 was chosen because it is quiet.** A scan from the PC showed OSU's
APs on 2.4 GHz channels 1/6/11 and 5 GHz 36–157, with nothing on 161 or 165. A
clear channel means measured CSI reflects the experiment rather than campus
traffic.

**The bands need different SSIDs.** Sharing one name lets clients roam between
radios, which changes the transmitting BSSID mid-experiment and silently breaks
a MAC filter.

**20 MHz** matches `csi-enable <ch>/20` and yields 64 subcarriers. Widen later if
you need finer frequency resolution — but beacons are sent at 20 MHz for
compatibility regardless, so a wide capture only helps with data traffic.

**Security must be enabled.** On first configuration both SSIDs came up open
(`SECURITY: --`). Beyond being a rogue-AP problem on a campus network, an open
network attracts stray clients, and every association makes the router transmit
unpredictably — destroying the steady frame rate that makes it useful as a
reference transmitter.

## Using it for CSI

```bash
# 5 GHz, filtered to this router's 5 GHz radio only.
# Beacons alone give ~10 Hz. csi-capture drives a separate client so the
# router transmits continuously - ~166 Hz measured. See
# ../docs/10-collection-method.md.
../bin/csi-capture csi.pcap 30
```

Expect ~10 frames/s at ~102.4 ms spacing from beacons alone (100 TU × 1024 µs).
The client must be a device OTHER than the Pi, and if it is a 2x2 client the
AP will rate-adapt to two spatial streams that the 1x1 Pi cannot decode — use
`--traffic bcast` (the default) or a 1x1 client. See
`../docs/10-collection-method.md`.

For higher rates, associate a client and have it generate traffic the **router**
transmits — the CSI MAC filter matches frames sent *from* that BSSID, so a client
pinging the router works (replies come from it) while traffic toward it does not.

## Verified performance

Measured 2026-08-27, Pi at ~2 m, 5 GHz radio, beacons only:

| Metric | Value |
|---|---|
| Valid CSI frames | **40/40** parsed, single source MAC |
| Source | `60:e3:27:fb:61:54` only — filter working, nothing else leaked in |
| chanspec reported by firmware | `0xd0a1` (0xa1 = 161) — matches configuration |
| RSSI | **-41 dBm** |
| Subcarriers | 64, none zero-valued |
| Rate | **9.8 frames/s** |
| Median inter-frame gap | **102.4 ms** (= 100 TU beacon interval) |
| Max gap | 204.8 ms — exactly 2x, i.e. one beacon missed |

The occasional doubled gap is a single dropped beacon (~97.5% capture rate),
normal for over-the-air reception and not a fault.

For comparison across the three transmitters tried:

| Source | RSSI | Sources in capture | Rate |
|---|---|---|---|
| Ambient campus APs | -66 dBm | 4 mixed | irregular |
| iPhone hotspot | -34 dBm | 1 | 10.0 /s, but sleeps after ~90 s |
| **TL-WDR4300 (this)** | **-41 dBm** | **1** | **9.8 /s, indefinitely** |

## Verifying it is up

```bash
nmcli dev wifi rescan; sleep 5
nmcli -f SSID,BSSID,CHAN,FREQ,SIGNAL,SECURITY dev wifi list | grep -i nexmon
```

## History

Arrived with an unknown admin password (`admin`/`admin` rejected by the form —
no `WWW-Authenticate` header, so it uses form auth, meaning the password had been
changed). Factory reset via the rear pinhole **Reset** button held ~10 s; the
reset was confirmed by watching the `Date:` response header, which doubles as an
uptime counter while the clock is unset — it dropped from `00:05:02` back to
`00:01:59`.
